# MolHalluLens 项目 Agent 工作规范

本文件规定 Agent 实施 MolHalluLens Molecule Editing Hallucination Pilot 时必须遵循的工作流。以下两个文件是任务执行的权威来源：

- `MOLHALLULENS_MOLEDIT_HALLUCINATION_IMPLEMENTATION_PLAN.md`：需求、设计约束、验收标准和技术真源。
- `MOLHALLULENS_MOLEDIT_HALLUCINATION_TASKS.json`：任务顺序、依赖、进度、证据和质量自评记录。

如果任务 JSON 与实施计划存在冲突，以实施计划中的冻结决定和明确约束为准。Agent 不得自行弱化约束；应将冲突记录为 blocker，并修正任务描述或请求人工决策。

## 一、核心执行原则

1. 严格按照 `tasks` 数组顺序推进，优先选择最靠前、状态为 `not_started`、且所有 `depends_on` 均已 `completed` 的任务。
2. 同一时间原则上只把一个任务设为 `in_progress`。任务确实可以独立并行时，也必须保证依赖全部完成、文件修改不冲突，并分别维护状态和证据。
3. 不得跳过任务、依赖、验收条件或实施计划中的 validation gate。不得为了推进进度而把失败任务标记为完成。
4. 每个任务开始前和完成后都必须阅读实施计划中与该任务有关的章节；不能只依赖任务标题或以前的记忆。
5. 每完成一个任务，必须立即更新任务 JSON，不得积攒多个任务后一次性补写。
6. `completed` 表示交付物真实存在、验收条件逐条通过且有可复核证据，而不是“代码已经写完”。
7. 必须保留用户已有修改，避免无关重构和破坏性操作。密钥、Authorization header、`POE_API_KEY` 不得进入源码、日志、测试快照、JSON 或 Git。

## 二、单个任务的标准工作流

### 1. 选择任务

打开 `MOLHALLULENS_MOLEDIT_HALLUCINATION_TASKS.json`：

1. 核对 `progress_summary` 与实际任务状态是否一致。
2. 从前向后找到第一个可执行任务。
3. 确认其全部 `depends_on` 已完成，并检查依赖任务的 evidence 和质量自评，而不是只看状态字符串。
4. 如果依赖未完成，先完成依赖；不得越过依赖直接实现。

### 2. 实施前核对计划

在修改代码前：

1. 完整阅读该任务的 `description`、`deliverables` 和 `acceptance_criteria`。
2. 在实施计划中定位并重新阅读所有相关章节，包括冻结决定、风险、测试和发布约束。
3. 检查任务是否遗漏了计划要求。如果有遗漏，应在不改变项目目标的前提下补齐实施范围，并在 `completion_notes` 说明。
4. 检查仓库当前状态、相关实现、测试和已有未提交修改，避免覆盖其他工作。
5. 明确本任务的最小实现范围、验证命令和预期证据。

### 3. 登记开始状态

开始实现前更新该任务：

```json
{
  "status": "in_progress",
  "assigned_to": "当前 agent 标识",
  "started_at": "带时区的 ISO 8601 时间",
  "blocker": null
}
```

同时更新顶层 `updated_at` 和 `progress_summary`。修改后必须运行 JSON 语法校验。

### 4. 实现任务

实施时必须遵守：

- 只实现当前任务及其正常所需的小范围配套改动。
- 实施计划中的冻结约束必须体现在类型、配置、断言、validator 或测试中，不能只写在注释里。
- 对异常、fallback、quota deviation、validator rejection 和 provenance 使用结构化记录，禁止 silent fallback。
- 新功能应有与风险相称的 unit、property、integration 或 golden tests。
- 对外部 API 使用 mock/cache 测试；只有任务明确需要且环境满足条件时才进行真实调用。
- 任何生成 artifact 都必须可追踪到输入、配置、版本、seed、验证报告或 content hash。

### 5. 验证任务

实现后逐项执行：

1. 运行最直接的单元测试和静态/语法检查。
2. 运行受影响模块的集成或 property tests。
3. 对照 `acceptance_criteria`，逐条收集证据。
4. 检查输出文件、数量、schema、hash、日志和 provenance 是否符合计划。
5. 检查是否引入 GT leakage、cross-split leakage、pre-token shift、裸 SMILES 等价判断、secret 泄漏或未声明 fallback。
6. 若测试无法运行，不能假定通过；应记录原因，并根据验收影响将任务保持 `in_progress` 或设为 `blocked`。

### 6. 完成后再次核对实施计划

在标记完成前，重新阅读相关实施计划章节，并回答：

- 实现是否覆盖计划要求，而不只是任务 JSON 的简写？
- 是否违反 13 项冻结决定中的任何一项？
- 是否满足该阶段退出条件？
- 是否实现了计划要求的失败处理、审计和测试？
- 是否产生额外的未标注行为、数据泄漏或 shortcut 风险？
- 是否需要更新配置、schema、文档、manifest 或 known limitations？

如答案存在不确定性，继续验证或记录 blocker，不得直接完成。

### 7. 在 JSON 中记录完成情况

只有验收条件全部通过后，更新任务对象：

```json
{
  "status": "completed",
  "completed_at": "带时区的 ISO 8601 时间",
  "completion_notes": "说明采用的设计、关键决策、偏差和最终结果",
  "evidence": ["测试报告、manifest、日志或 artifact 路径"],
  "files_changed": ["本任务新增或修改的文件"],
  "verification_commands": ["实际执行并通过的命令"],
  "blocker": null
}
```

`completion_notes` 必须说明“怎么完成的”，不能只写“完成”或“测试通过”。`verification_commands` 只能记录真正执行过的命令。

### 8. 记录完成质量自评

每个完成任务必须在顶层 `quality_assessment_log` 追加一条记录，并符合 `quality_assessment_schema`。自评至少包含：

- `requirements_alignment`
- `implementation_quality`
- `verification_coverage`
- `documentation_and_traceability`
- `overall_score`
- 完成后重新核对的计划章节
- 每条验收条件是否通过及其证据
- 优点、已知不足、后续动作和总体评价

评分使用 1–5：

- 5：完全满足，证据充分，无已知重要缺口。
- 4：满足核心要求，仅有不影响验收的小问题。
- 3：基本可用但存在明显缺口；通常不应标记 completed，除非缺口明确不属于本任务验收范围。
- 2：部分实现或验证明显不足，不得标记 completed。
- 1：未达到任务目标，不得标记 completed。

任何验收条件失败，或任一质量维度低于 4 时，任务原则上保持 `in_progress`；若无法继续，则设为 `blocked`。已知不足必须如实记录，禁止为了提高分数而省略问题。

### 9. 更新总体进度并校验 JSON

任务状态变化后同步更新：

- `updated_at`
- `progress_summary.not_started`
- `progress_summary.in_progress`
- `progress_summary.blocked`
- `progress_summary.completed`
- `progress_summary.last_completed_task`

必须保证四种状态计数之和等于 `total_tasks`，任务 ID 唯一，所有 dependency ID 存在。至少执行：

```bash
python -m json.tool Pilot/Blueprint/MOLHALLULENS_MOLEDIT_HALLUCINATION_TASKS.json >/dev/null
```

建议同时运行一个一致性检查，验证状态统计、依赖顺序，以及每个 completed 任务都有对应质量自评。

## 三、阻塞处理

任务无法继续时，将 `status` 设为 `blocked`，并填写：

```json
{
  "blocker": {
    "reason": "具体阻塞原因",
    "attempts": ["已经尝试的排查或替代方案"],
    "required_to_unblock": "需要的输入、权限、资源或决策",
    "blocked_at": "带时区的 ISO 8601 时间"
  }
}
```

常见阻塞包括缺少明确的 benchmark 使用决策、Poe 认证或 points、模型 capability 改变、依赖无法安装、数据异常无法在冻结约束下解决。阻塞不授权 Agent 放宽 sanitize、改变 split、切换模型、修改 phenotype 或接受不完整 bundle。

## 四、提交和交接要求

每次交接应简明报告：

1. 完成或阻塞的 task ID 和标题。
2. 主要实现结果。
3. 实际运行的验证及结果。
4. JSON 中记录的总体质量分数和已知不足。
5. 下一个可执行任务 ID。

不得声称整个阶段或项目完成，除非对应退出条件或发布验收条件全部通过。最终 `pilot_v1` 只能在 T052 完成、发布清单全部通过并冻结 manifest/hash 后宣布完成。
